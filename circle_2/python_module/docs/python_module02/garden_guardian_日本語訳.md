## 第I章 序文

農業データエンジニアリングの世界へようこそ！

Pythonの基礎（モジュール00）とガーデン監視クラス（モジュール01）で学んだことを土台に、いよいよスマート農業の本当の課題に取り組む準備が整いました。現代の農業では、灌漑システムを流れる水のようにデータが流れています——センサーの読み取り値が絶えずストリームで送られてきて、天気APIが予報を提供し、IoTデバイスが土壌のpHから温室の湿度まであらゆるものを監視しています。

しかし、このデータパイプラインが乱気流に見舞われたらどうなるでしょうか？収穫期にセンサーが故障したら？重要な監視期間中にネットワーク接続が切れたら？破損したデータが誤った灌漑サイクルを引き起こしそうになったら？

プロの農業データエンジニアは、堅牢なシステムとは障害を避けるために作られるものではなく、**予期せぬ事態を優雅に処理する**ように設計されるものだと知っています。あなたのデジタル温室は、自然そのものと同じくらい強靭である必要があります。

Pythonの**例外処理（exception handling）**システムは、防弾仕様の農業データパイプラインを構築するためのツールキットです。**センサーの異常を捕捉**し、**カスタムの農業アラート**を作成し、母なる自然（あるいはマーフィーの法則）が牙をむいたときでも**データの整合性を確保する**方法を学んでいきます。

このプロジェクトでは、基本的なプログラマーから農業データエンジニアへと進化し、予期せぬことが起きても成長し続ける監視システムを構築していきます。

## 第V章 演習0: 農業データの検証

| 項目 | 内容 |
|---|---|
| ファイル名 | ft_first_exception |
| ディレクトリ | ex0/ |
| 提出ファイル | ft_first_exception.py |

あなたのスマート農業データパイプラインは、圃場センサーから気温の読み取り値を受け取ります。センサーが破損したデータを送信したり、農家がモバイルアプリを通じて無効な値を入力したりすることがあります。あなたのデータ検証層は、農業分析データが破損する前に、不正なデータをフィルタリングする必要があります。

以下を行うシンプルな関数 `input_temperature(temp_str)` を書いてください:

- 入力文字列をパラメータとして受け取る
- それを数値に変換する
- 気温を整数として返す

次に、`input_temperature()` に対して以下のテストを行う関数 `test_temperature()` を書いてください:

- 有効な入力（"25"）を使用する
- 無効な入力（"abc"）を使用する
- `input_temperature()` が失敗した場合を処理し、エラーメッセージを表示する
- エラーが発生してもプログラムが動作し続けることを示す

**出力例:**
```
$> python3 ft_first_exception.py
```

> 基底の Exception クラスを使ってもよいですし、`input_temperature()` がどの例外を発生させうるかを調べてもよいでしょう。

## 第VII章 演習2: さまざまな種類の問題

| 項目 | 内容 |
|---|---|
| ファイル名 | ft_different_errors |
| ディレクトリ | ex2/ |
| 提出ファイル | ft_different_errors.py |
| 許可された関数 | print(), open(), int() |

あなたのガーデンプログラムは、さまざまな種類の問題に遭遇するかもしれません。Pythonには状況に応じたさまざまな種類のエラーがあり、それらを個別に、あるいはまとめて捕捉することができます。

不正なコードを含む関数 `garden_operations(operation_number)` を書いてください。`operation_number` が0から3の各値の場合、それぞれ異なる不正なコードが以下のいずれかの例外を発生させます:

- `ValueError` — 不正なデータが与えられたとき（`int()` に数値の代わりに "abc" を渡すなど）
- `ZeroDivisionError` — ゼロで割ろうとしたとき
- `FileNotFoundError` — 存在しないファイルを開こうとしたとき（開けていない場合は `close()` する必要はありません）
- `TypeError` — 混在できない異なる型を混ぜようとしたとき（文字列と数値を足そうとしませんでしたか？）

`operation_number` のそれ以外の値には不正なコードは含まれず、単に return するだけです。

以下を行う `test_error_types()` 関数を作成してください:

- 各種類のエラーが発生する様子を示す
- 各エラーを捕捉し、何が問題だったかを説明する
- 各エラーの後もプログラムが実行し続けることを示す
- 1つの `try:` ブロックで複数の種類のエラーを捕捉する方法を示す

**出力例:**
```
$> python3 ft_different_errors.py
=== Garden Error Types Demo ===
Testing operation 0...
Caught ValueError: invalid literal for int() with base 10: 'abc'
Testing operation 1...
Caught ZeroDivisionError: division by zero
Testing operation 2...
Caught FileNotFoundError: [Errno 2] No such file or directory: '/non/existent/file'
Testing operation 3...
Caught TypeError: can only concatenate str (not "int") to str
Testing operation 4...
Operation completed successfully

All error types tested successfully!
```

> なぜPythonにはさまざまな種類のエラーがあるのでしょうか？1つの `try:` だけで**複数の種類**のエラーをどうやって捕捉できるでしょうか？`type()` は使えないことに注意してください。

> mypyは、TypeErrorを発生させる不正なコードに対してエラーを表示します。それがmypyの仕事です！ですので、この例外をテストするためには、このエラーを意図的に残しておく必要があります。

> `open()` はすでにCで経験済みでしょう。Pythonでの使い方はとても簡単です。

- 特定のエラー型を捕捉する方法を示す

## 第IX章 演習4: finallyブロック——常に後始末をする

| 項目 | 内容 |
|---|---|
| ファイル名 | ft_finally_block |
| ディレクトリ | ex4/ |
| 提出ファイル | ft_finally_block.py |
| 許可された関数 | print(), str.capitalize() |

あなたのガーデンプログラムは、エラーが発生した場合でもリソースの後始末をする必要があります。`finally` ブロックはこれに最適です——エラーの有無にかかわらず、常に実行されます。

以下を行う関数 `water_plant(plant_name)` を書いてください:

- 植物に水をやろうとする
- 植物名が大文字で始まっていれば成功する
- 植物名が大文字で始まっていなければエラーを発生させる（前の演習の `PlantError` 例外を使用すること）
- 成功時にメッセージを表示する

以下を行う関数 `test_watering_system()` を作成してください:

- 灌水システムを開く（メッセージを表示するだけでよい）
- `water_plant()` を使って複数の植物に水をやる
- try/except/finally の構造を使用する
- 植物名が無効で水をやれない場合のエラーを処理する。その場合、テストを中止し、直ちに main に戻ること
- `finally` ブロックで常に灌水システムを閉じる
- エラーが発生しても後始末が常に行われることを示す

**出力例:**
```
$> python3 ft_finally_block.py
=== Garden Watering System ===

Testing valid plants...
Opening watering system
Watering Tomato: [OK]
Watering Lettuce: [OK]
Watering Carrots: [OK]
Closing watering system

Testing invalid plants...
Opening watering system
Watering Tomato: [OK]
Caught PlantError: Invalid plant name to water: 'lettuce'
.. ending tests and returning to main
Closing watering system

Cleanup always happens, even with errors!
```

> エラーが発生した場合でもリソースの後始末をすることがなぜ重要なのでしょうか？`finally` ブロックは、後始末が常に行われることをどのように保証するのでしょうか？
