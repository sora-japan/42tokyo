## get_next_line.h

```c
13  #ifndef GET_NEXT_LINE_H
14  # define GET_NEXT_LINE_H
15
16  # include <stdlib.h>
17  # include <unistd.h>
18
19  # ifndef BUFFER_SIZE
20  #  define BUFFER_SIZE 42
21  # endif
22
23  # ifndef LINE_DELIMITER
24  #  define LINE_DELIMITER '\n'
25  # endif
26
27  typedef struct s_save
28  {
29      char    *data;
30      size_t  off;
31      size_t  len;
32      size_t  cap;
33  }   t_save;
```

| 行 | 何をしているか |
| --- | --- |
| 13–14 | **インクルードガード**。同じヘッダが2回展開されると `t_save` の再定義エラーになる。`#ifndef` で2回目を丸ごと飛ばす |
| 16 | `malloc` / `free` の宣言。`size_t` 型の定義もここから来る |
| 17 | `read` の宣言。`ssize_t` もここ |
| 19–21 | **`-D BUFFER_SIZE` が無いときだけ 42 を使う**。`-D` はコンパイラがコマンドラインで `#define` するのと同じなので、`#ifndef` が偽になり 20 行目は展開されない。subject の「`-D` の有無どちらでもコンパイルできること」はこの3行で満たしている。**この3行を消すと、`-D` 無しのコンパイルが `error: use of undeclared identifier 'BUFFER_SIZE'` で失敗する**（実測）。値が `42` である必然性は無く、任意の正の整数でよい（subject のコンパイル例が 42 なので合わせただけ） |
| 23–25 | 区切り文字も同じ仕組みでコンパイル時に差し替え可能にしたもの。既定は `'\n'` なので、`-D` を付けなければ挙動は変わらない。**`#` の後は空白2つ** — インクルードガードの内側でネストが深さ2 なので、空白1つだと Norm エラー `PREPROC_BAD_INDENT` になる（実測） |
| 29 | 持ち越しバイト列。**`\0` 終端していない**。長さは必ず `len` で判断する |
| 30 | 有効データの**開始位置**。行を返したあと、残りを先頭へコピーし直す代わりにこれを進める |
| 31 | いま入っている有効バイト数 |
| 32 | `malloc` で確保済みのバイト数。`off + len ≤ cap` が常に成り立つ |

**3つの数を分けている意味**（この実装で一番大事な設計判断）:

```
cap = 10 の確保済み領域
┌───┬───┬───┬───┬───┬───┬───┬───┬───┬───┐
│ a │ b │ \n│ c │ c │ c │ ? │ ? │ ? │ ? │
└───┴───┴───┴───┴───┴───┴───┴───┴───┴───┘
 ←─ 消費済み ─→ ←── len = 3 ──→ ←─ 未使用 ─→
              ↑ off = 3
```

- `cap` は「入れ物」— 余裕がある限り `malloc` を呼ばない
- `len` は「中身の量」— 長さを数え直さない
- `off` は「中身の位置」— 行を返すたびに残りをコピーし直さない

`off` を持たず毎回先頭へ詰め直す設計にすると、`BUFFER_SIZE` が大きいときに実行時間が `O(行数 × 残りバイト数)` に膨らみます（[実測](#consume--開始位置を進めるだけ)）。

## nl_pos — 区切り文字を探す

`get_next_line_utils.c:15-27`

```c
15  ssize_t nl_pos(t_save *s, size_t from)
16  {
17      size_t  i;
18
19      i = from;
20      while (i < s->len)
21      {
22          if (s->data[s->off + i] == LINE_DELIMITER)
23              return ((ssize_t)i);
24          i++;
25      }
26      return (-1);
27  }
```

| 行 | 何をしているか / なぜ必要か |
| --- | --- |
| 15 | 戻り値が **`ssize_t`（符号付き）**。「見つからない」を `-1` で表すため。`size_t` は符号なしなので `-1` が `18446744073709551615` になり、`>= 0` の判定が常に真になって壊れる |
| 15 | 引数 `from` — **どこから探し始めるか**。追記直後は「新しく読んだ範囲」の先頭を渡す。これが無いと毎回先頭から走査し直して `O(N²)` になる |
| 20 | `s->data[i] != '\0'` ではなく **`i < s->len`** で終端判定。`data` は `\0` 終端していないので、`\0` を目印にすると確保領域の外まで読みに行く |
| 22 | 添字が **`s->off + i`**。`i` は「有効データの先頭から数えた位置」、実際のメモリ上の位置は `off` だけずれている。**この関数が返すのも `i`（相対位置）** で、`off` を足した絶対位置ではない点が重要 |
| 22 | **実装全体で区切り文字と比較しているのはこの1行だけ**。`str_line` は `nl_pos` の戻り値から長さを出すだけ、`fill_save` は判断を委ねるだけ、`grow` / `append` / `consume` はバイトの中身を見ない。だから区切り文字の変更がここ1か所で完結する。`\r\n` は考慮していない（subject の要求外） |
| 23 | 見つかった位置を返す。**区切り文字そのものの位置**であって、行の長さではない点に注意（長さは呼び出し側で `+1` する） |
| 26 | 最後まで無ければ `-1`。これは「EOF まで読んだ最終行」と「まだ読み足りない」の両方で起きるので、**呼び出し側が文脈で判断する** |

### 壊すとどうなるか（実測）

| 変更 | 結果 |
| --- | --- |
| 戻り値を `size_t` にする | `-1` が巨大な正数になり「常に `\n` が見つかった」扱い。1文字目で行を切ってしまう |
| `i < s->len` を `s->data[i]` にする | `data` は `\0` 終端していないので確保領域外を読む（未定義動作） |
| `from` を使わず常に 0 から探す | 出力は正しいが、長い行で走査が `O(N²)` になる |

## grow — 容量を2倍ずつ広げる

`get_next_line.c:15-41`

```c
15  static int  grow(t_save *s, size_t need)
16  {
17      char    *new;
18      size_t  cap;
19      size_t  i;
20
21      if (need <= s->cap)
22          return (1);
23      cap = s->cap;
24      if (cap == 0)
25          cap = BUFFER_SIZE + 1;
26      while (cap < need)
27          cap *= 2;
28      new = malloc(cap);
29      if (!new)
30          return (0);
31      i = 0;
32      while (i < s->len)
33      {
34          new[i] = s->data[i];
35          i++;
36      }
37      free(s->data);
38      s->data = new;
39      s->cap = cap;
40      return (1);
41  }
```

| 行 | 何をしているか / なぜ必要か |
| --- | --- |
| 15 | **`static`** — このファイルの外から見えない。Norm の関数数制限（1ファイル5個）内に収めつつ、公開したくない内部関数を隠す |
| 15 | 戻り値は「成功=1 / 失敗=0」。`malloc` 失敗を呼び出し側に伝える唯一の手段 |
| 21–22 | **この実装の性能の核心**。容量が足りていれば `malloc` を一切呼ばず即座に帰る。2行目以降はほぼ毎回ここで返る |
| 23 | 現在の容量から始める |
| 24–25 | 初回（`cap == 0`）だけ `BUFFER_SIZE + 1` を種にする。`read` 1回分（最大 `BUFFER_SIZE` バイト）が必ず収まるサイズ。**`+1` は保険**で、`BUFFER_SIZE` ちょうどでも論理的には足りる |
| 26–27 | **足りるまで倍々**。`need` ちょうどではなく倍にするのがポイント。1回の拡張で次の何度かの追記を先払いしておくことで、拡張回数が `log₂(N)` に落ちる |
| 28–30 | 新しい領域を確保。失敗したら **`s` を一切変更せずに** `0` を返す。ここで `s->data` を書き換えてしまうと、失敗時に古いポインタを失って解放できなくなる |
| 31–36 | 既存の中身をコピー。コピーするのは **`len` バイトだけ**（`cap` バイトではない）。未使用部分の中身は意味を持たない |
| 37 | 古い領域を解放。**初回は `s->data` が `NULL`** だが、`free(NULL)` は C 標準で何もしないと定められているので分岐は不要 |
| 38–39 | 差し替え。`len` は変わらない（中身の量は増えていない） |

### なぜ「倍」なのか

`need` ぴったりに確保すると、追記のたびに `malloc` + 全コピーが起きます。長さ `N` の行では合計 `O(N²/BUFFER_SIZE)` バイトのコピー。倍にすると拡張は `log₂(N)` 回、コピー総量は `1 + 2 + 4 + … + N < 2N` で `O(N)`。**1バイトあたりの平均コストが定数** = 償却計算量 `O(1)`。

### 壊すとどうなるか（実測）

`'x' × 20000` の1行を含むファイルで計測。

| 変更 | 結果 |
| --- | --- |
| 21–22 の早期 return を消す | **`BUFFER_SIZE=10` で malloc 16回 → 2006回**、`42` で 14回 → 482回。素朴な実装と同じ回数まで悪化する。この2行だけが速さの正体 |
| 24–25 の `cap == 0` を消す | **無限ループでハングした**（2秒で強制終了）。`cap` が 0 のままだと 27 行目の `cap *= 2` が `0 * 2 = 0` を繰り返し、`while (cap < need)` を永遠に抜けられない |
| 37 の `free` を消す | **`leaks` が 14 leaks / 32800 bytes を報告**（正常版は 0） |
| 26–27 を `cap = need` にする | 動くが malloc 回数が上の「早期 return を消した場合」とほぼ同じまで増える |

## compact — 先頭へ寄せる

`get_next_line.c:43-54`

```c
43  static void compact(t_save *s)
44  {
45      size_t  i;
46
47      i = 0;
48      while (i < s->len)
49      {
50          s->data[i] = s->data[s->off + i];
51          i++;
52      }
53      s->off = 0;
54  }
```

`consume()` が `off` を進めるだけなので、バッファ前方には消費済みの死んだ領域が溜まります。**追記が必要になったときだけ**、有効データを先頭へ寄せてその領域を回収するのがこの関数です。

| 行 | 何をしているか / なぜ必要か |
| --- | --- |
| 48–52 | 有効データ `len` バイトを `off` の位置から先頭へコピー。前から順にコピーするので、コピー元がコピー先より必ず後ろ = 上書きで壊れない |
| 53 | `off` をリセット。これ以降、`data[0]` が有効データの先頭になる |

**呼ばれる頻度が少ないことが性能の前提です。** `append` から `read()` 1回につき高々1度しか呼ばれず、寄せる量もそのときの持ち越し分だけなので、全体としては入力サイズに比例するコストに収まります。`BUFFER_SIZE` が大きい場合は1回目の `read` でファイル全体が載り、以降の呼び出しはほぼ `nl_pos` の早期 return で終わるため、そもそもほとんど呼ばれません。

## append — 末尾に追記する

`get_next_line.c:56-72`

```c
56  static int  append(t_save *s, char *buf, size_t n)
57  {
58      size_t  i;
59
60      if (s->off != 0)
61          compact(s);
62      if (!grow(s, s->len + n))
63          return (0);
64      i = 0;
65      while (i < n)
66      {
67          s->data[s->len + i] = buf[i];
68          i++;
69      }
70      s->len += n;
71      return (1);
72  }
```

| 行 | 何をしているか / なぜ必要か |
| --- | --- |
| 60–61 | **追記の前に必ず `off` を 0 に戻す**。これ以降 63–70 行と `grow` は「有効データは `data[0]` から始まる」という前提で書けるので、添字に `off` を足す必要がなくなる。`off == 0` のときは何もしない（無駄なコピーを避ける） |
| 62 | **必要量は「今ある分 + 足す分」**。`n` だけでは足りない。`grow` が失敗（`malloc` 失敗）したらここで中断 |
| 63 | 失敗を伝播。`s` は `grow` が触っていないので無傷のまま |
| 65–69 | `s->len` の位置から `n` バイト書き込む。**上書きではなく追記**なので開始位置が `s->len + i`（60–61 行で `off == 0` が保証されている） |
| 70 | **コピーが全部終わってから** `len` を進める。先に進めると 67 行目の書き込み位置がずれる |
| 71 | 成功 |

`n == 0`（EOF）でも安全に動きます。`grow(s, len+0)` は必ず早期 return し、ループは0回、`len` は変わりません。この「何もしない」が `fill_save` の EOF 処理を単純にしています。

### 壊すとどうなるか

| 変更 | 結果 |
| --- | --- |
| 60–61 の `compact` 呼び出しを消す | `grow` が `data[0]` から `len` バイトをコピーするため、`off > 0` のときに**消費済みの古いバイトを有効データとして拾ってしまう**。67 行の書き込み位置も `off` 分ずれて確保領域外に出る |
| 60 の `if (s->off != 0)` を消して常に `compact` | 動作は正しいが、`off == 0` のときにも全バイトを自分自身へコピーする無駄が出る |

## fill_save — 必要な分だけ読む

`get_next_line.c:74-99`

```c
74  static int  fill_save(int fd, t_save *s)
75  {
76      char    *buf;
77      ssize_t n;
78      size_t  start;
79
80      if (nl_pos(s, 0) >= 0)
81          return (1);
82      buf = malloc(BUFFER_SIZE);
83      if (!buf)
84          return (0);
85      n = 1;
86      while (n > 0)
87      {
88          n = read(fd, buf, BUFFER_SIZE);
89          if (n < 0)
90              return (free(buf), 0);
91          start = s->len;
92          if (!append(s, buf, (size_t)n))
93              return (free(buf), 0);
94          if (nl_pos(s, start) >= 0)
95              break ;
96      }
97      free(buf);
98      return (1);
99  }
```

| 行 | 何をしているか / なぜ必要か |
| --- | --- |
| 80–81 | **持ち越しの中に既に区切り文字があれば `read` を1回も呼ばない**。単なる最適化ではなく、**正しさの要件**（下の実測を参照）。`malloc(buf)` より前に判定しているので確保すら発生しない |
| 82–84 | 読み込み用の一時バッファ。**`char buf[BUFFER_SIZE];` とスタックに取らず `malloc` でヒープに取る**のが重要（下の実測を参照）。`get_next_line` の呼び出しごとに確保・解放する。`static` にすれば節約できるが `static` を増やしたくないので毎回確保 |
| 85 | ループに入るためのダミー初期値。`n` が未初期化のまま 86 行目に入るのを防ぐ |
| 86 | `n > 0` が続く限り読む。`n == 0`（EOF）で自然に抜ける |
| 88 | `read` の戻り値は3種類 — `-1`（エラー）/ `0`（EOF）/ 正の値（実際に読めたバイト数）。**要求した `BUFFER_SIZE` より少ないことは普通にある**（パイプ・端末では日常的） |
| 89–90 | エラーは即座に失敗。**ここで抜けないと** 92 行目で `(size_t)(-1)` = 巨大な値が `append` に渡り、`grow` が天文学的なサイズを要求して落ちる |
| 90 | `return (free(buf), 0)` はカンマ演算子。`free` してから `0` を返す。Norm の行数制限内で「解放してから return」を1行で書くための書き方 |
| 91 | **追記前の位置を覚える**。次の `nl_pos` に渡して「新しく読んだ範囲だけ」を走査するため。`nl_pos` も `s->len` も `off` を除いた相対位置なので、`append` の中で `compact` が走って `off` が変わっても**この値はずれない** |
| 92–93 | 追記。失敗（`malloc` 失敗）なら `buf` を解放して失敗を返す。`s->data` は `grow` が守っているので二重解放は起きない |
| 94–95 | **新しく読んだ範囲に区切り文字があれば読むのをやめる**。ここが「ファイル全体を読むな」という subject の要求を満たす箇所。`start` から探すので、既に走査済みの部分を見直さない |
| 97–98 | 正常終了。EOF で抜けた場合もここを通る（`s->len == 0` かどうかの判断は呼び出し側の仕事） |

### 80–81 行が「最適化」ではない理由（実測）

`BUFFER_SIZE=8` で `printf 'a\nbb\n'` をパイプで流し、**パイプを開いたまま** 2行読ませた結果:

| 版 | 結果 |
| --- | --- |
| 正常版 | `1st=a` `2nd=bb` `done` — 即座に完了 |
| 80–81 を消した版 | **2行目でハング**（2秒で強制終了） |

1回目の `read` で `"a\nbb\n"` が全部バッファに入り、`"bb\n"` が持ち越されます。2行目の要求は本来この持ち越しだけで返せるのに、80–81 が無いと `read` を呼びに行き、**書き手が次のデータを送るまでブロック**します。端末から `while (gnl(0))` で読むプログラムは、1行入力するたびに固まって使い物になりません。

なお通常ファイルでは EOF が即座に返るため、この違いは表に出ません。**ファイルでテストしているだけでは発見できないバグ**の典型例です。

### その他の壊し方（実測）

| 変更 | 結果 |
| --- | --- |
| 82 を `char buf[BUFFER_SIZE];` にする（スタック確保） | `BUFFER_SIZE=10000000` で **SIGSEGV**。10MB をスタックに取ろうとして溢れる（macOS の既定スタックは 8MB）。`malloc` ならヒープなので `10000000` でも完走する。**subject が `10000000` を例示しているのはここを踏ませるため** |
| 89–90 の `n < 0` チェックを消す | `(size_t)(-1)` が `append` に渡り、`grow` が `SIZE_MAX` 級の確保を要求 → `malloc` 失敗で `NULL` が返るか、その手前で落ちる |
| 91 の `start` を使わず `nl_pos(s, 0)` にする | 出力は正しい。長い行で走査量が `O(N²)` になるだけ |
| 94–95 の `break` を消す | ファイル全体を読み切ってから最初の行を返す。出力は正しいが subject の「全部読んでから処理するな」に違反 |

## str_line — 行を切り出す

`get_next_line_utils.c:38-60`

```c
38  char    *str_line(t_save *s, size_t *len)
39  {
40      char    *line;
41      ssize_t pos;
42      size_t  i;
43
44      pos = nl_pos(s, 0);
45      if (pos < 0)
46          *len = s->len;
47      else
48          *len = (size_t)pos + 1;
49      line = malloc(*len + 1);
50      if (!line)
51          return (NULL);
52      i = 0;
53      while (i < *len)
54      {
55          line[i] = s->data[s->off + i];
56          i++;
57      }
58      line[i] = '\0';
59      return (line);
60  }
```

| 行 | 何をしているか / なぜ必要か |
| --- | --- |
| 38 | `len` は**出力引数**。切り出した長さを呼び出し側に返すため。C は多値を返せないので、行本体を戻り値・長さをポインタで返す |
| 44 | 先頭から区切り文字を探す。ここは `from = 0` でよい（有効データの先頭が行の先頭だから） |
| 45–46 | **区切り文字が無い = EOF まで読み切った最終行**。持ち越し全部が1行になる |
| 47–48 | 区切り文字があれば **`pos + 1`**。`+1` で区切り文字自身を行に含める。subject の「返す行は `\n` を含む」という指定はこの1文字 |
| 49 | 確保サイズは `*len + 1`。`+1` は `\0` の分。**ちょうどのサイズ**しか取らない（テスターはここも見る） |
| 50–51 | 失敗したら `NULL`。`s` は無傷なので、呼び出し側が `reset_save` で解放できる |
| 53–57 | `*len` バイトをコピー。コピー元の添字が **`s->off + i`**（有効データは先頭にあるとは限らない）。`data` は `\0` 終端していないので `strcpy` 的な発想は使えない |
| 58 | **`\0` 終端**。呼び出し側は `printf("%s")` などで文字列として扱うので必須。ループ終了時 `i == *len` なので最後の1バイトにちょうど入る |

### 壊すとどうなるか（実測）

| 変更 | 結果 |
| --- | --- |
| 48 の `+ 1` を消す | **無限に空行を返し続ける**。区切り文字が持ち越しに残り、次の呼び出しで `pos = 0` → `*len = 0` → 空文字列を返して `consume(0)` は何も捨てない、が永遠に繰り返される |
| 55 の `s->off +` を消す | 2行目以降が**消費済みの古いバイトを返す**（1行目だけ正しく見えるので気付きにくい） |
| 58 の `\0` 終端を消す | **この環境では正常に見えた**（新しいヒープページがゼロで埋まっていたため、たまたま `\0` があった）。未定義動作なので環境やタイミングで壊れる。**「テストが通る = 正しい」ではない**ことの実例 |
| 49 を `malloc(*len)` にする | 58 行目が確保領域の1バイト外に書き込む（ヒープ破壊） |

## consume — 開始位置を進めるだけ

`get_next_line_utils.c:62-68`

```c
62  void    consume(t_save *s, size_t len)
63  {
64      s->off += len;
65      s->len -= len;
66      if (s->len == 0)
67          s->off = 0;
68  }
```

**`malloc` も `free` もコピーもしません。** 数を2つ動かすだけの O(1) です。

```
consume(s, 3) の前:                 consume(s, 3) の後:
┌───┬───┬───┬───┬───┬───┐           ┌───┬───┬───┬───┬───┬───┐
│ b │ b │ \n│ c │ c │ c │           │ b │ b │ \n│ c │ c │ c │
└───┴───┴───┴───┴───┴───┘           └───┴───┴───┴───┴───┴───┘
 ↑ off=0   ←── len=6 ──→             ←消費済み→ ↑ off=3 ← len=3 →
                                     （メモリは1バイトも動いていない）
```

| 行 | 何をしているか / なぜ必要か |
| --- | --- |
| 62 | 戻り値なし。失敗しようがない（確保しないので） |
| 64 | 開始位置を返した分だけ前へ。**残りのバイトは動かさない** |
| 65 | 有効バイト数を減らす。`len` は常に「`off` から先に何バイトあるか」 |
| 66–67 | 使い切ったら `off` をリセット。**これが無いと `off` が単調増加し続け**、`compact` が呼ばれるまで前方の領域が無駄になる。ここで戻しておけば、行がぴったり消費されるたびにバッファを先頭から再利用できる |
| — | **`cap` は減らさない**。確保済み領域をそのまま次の行で使い回すのが狙い。「解放し忘れでは？」と聞かれたら「意図的な再利用。`NULL` を返すときに `reset_save` で必ず解放している」と答える |

### なぜ「前詰め」をやめたのか（実測）

かつてはここで `memmove` 相当の前詰めをしていました。`malloc` は増えないので一見よさそうですが、**1行返すたびに残り全部をコピーする**ため、`BUFFER_SIZE` が大きくてバッファにファイル全体が載っているときに `O(行数 × 残りバイト数)` に膨らみます。

20万行 2.3MB のファイルを読み切るまでの時間:

| `BUFFER_SIZE` | 前詰め方式 | `off` 方式（現在） |
| --- | --- | --- |
| `1` | 0.90 秒 | 0.88 秒 |
| `42` | 0.24 秒 | 0.22 秒 |
| `9999` | 1.25 秒 | 0.19 秒 |
| `1000000` | 約 230 秒 | 0.20 秒 |
| `10000000` | **234 秒以上（打ち切り）** | **0.19 秒** |

行数を2倍にすると前詰め方式は時間が約4倍になりました（10000行 0.52秒 → 20000行 2.25秒 → 40000行 9.32秒）。典型的な `O(N²)` です。**小さい `BUFFER_SIZE` では持ち越しが数十バイトしかないため表面化せず、小さいファイルでも表面化しません。**「大きい `BUFFER_SIZE`」と「多い行数」が揃ったときだけ出ます。

subject が `BUFFER_SIZE` の例として `10000000` を挙げていることを考えると、ここは踏みにいく価値のある落とし穴でした。

### 壊すとどうなるか（実測）

| 変更 | 結果 |
| --- | --- |
| 66–67 の `off` リセットを消す | 出力は正しいが、`off` が戻らないぶん `compact` の呼び出しと確保サイズが増える |
| 65 を `s->len = 0` にする | 残りを毎回捨てるので、1行返すごとに次の行が消える |
| `off` を使わず前詰めに戻す | 上の表のとおり `BUFFER_SIZE` が大きいときに `O(N²)` |

## reset_save — 全部捨てる

`get_next_line_utils.c:29-36`

```c
29  void    reset_save(t_save *s)
30  {
31      free(s->data);
32      s->data = NULL;
33      s->off = 0;
34      s->len = 0;
35      s->cap = 0;
36  }
```

| 行 | 何をしているか / なぜ必要か |
| --- | --- |
| 31 | 解放。`data` が `NULL` でも `free(NULL)` は安全なので分岐不要 |
| 32 | **`NULL` を代入するのが重要**。これを忘れると解放済みポインタが残り、次の呼び出しで二重解放になる |
| 33 | `off` も戻す。**これを忘れると**、次に同じ fd を開き直したとき `data[off + i]` が確保直後の領域の外を指す |
| 34–35 | 長さと容量もゼロに戻す。`data = NULL` なのに `cap` が残っていると `grow` が「容量は足りている」と誤判断して `NULL` に書き込む |

この関数が呼ばれた後の `s` は、**初期状態（ゼロ初期化直後）と完全に同じ**です。だから同じ fd を閉じて開き直しても、別の fd に切り替えても、先頭から正しく読み直せます。フィールドを増やしたら**必ずここにも追加する**必要がある、という点で保守上の要注意箇所です。

## get_next_line — 司令塔

`get_next_line.c:101-122`

```c
101 char    *get_next_line(int fd)
102 {
103     static t_save   s;
104     char            *line;
105     size_t          len;
106
107     if (fd < 0 || BUFFER_SIZE <= 0)
108         return (NULL);
109     if (!fill_save(fd, &s) || s.len == 0)
110     {
111         reset_save(&s);
112         return (NULL);
113     }
114     line = str_line(&s, &len);
115     if (!line)
116     {
117         reset_save(&s);
118         return (NULL);
119     }
120     consume(&s, len);
121     return (line);
122 }
```

| 行 | 何をしているか / なぜ必要か |
| --- | --- |
| 103 | **唯一の `static`**。関数を抜けても消えず、プログラム終了まで生きる。明示的な初期化子が無い `static` は **C 標準でゼロ初期化**されるので、初回は `{NULL, 0, 0, 0}` から始まる。グローバル変数と生存期間は同じだが、スコープが関数内に閉じているので subject の「グローバル変数禁止」に抵触しない |
| 107 | `fd < 0` は不正な fd。`BUFFER_SIZE <= 0` はコンパイル時定数の比較なので、最適化で消える（実行時コストはゼロ）。`-D BUFFER_SIZE=0` でコンパイルされても `malloc(0)` や無限ループにならない保険 |
| 109 | `fill_save` の失敗（read エラー / malloc 失敗）と、`s.len == 0`（何も読めなかった = EOF）を**同じ扱い**にする。**短絡評価の順序が重要** — `fill_save` を先に呼ばないと `s.len` が更新されない |
| 111 | **`NULL` を返す前に必ず解放**。これで「`NULL` が返った時点で内部メモリはゼロ」という不変条件が成立する |
| 114 | 行を切り出す。`len` に切り出した長さが書き戻される |
| 115–119 | `malloc` 失敗も同じ扱い。**`NULL` を返す経路が3つとも `reset_save` を通っている**のがこの関数の設計 |
| 120 | 消費を記録する。**`str_line` が返した `len` をそのまま渡す**ので、区切り文字を含めた正確な長さぶん `off` が進む |
| 121 | 呼び出し側が `free` する責任を持つ |

### 壊すとどうなるか（実測）

| 変更 | 結果 |
| --- | --- |
| 103 の `static` を外す | **SIGBUS でクラッシュ**（exit code 138）。未初期化のスタック領域をバッファのポインタとして `free` しに行く |
| 111 / 117 の `reset_save` を消す | EOF 到達時に持ち越しバッファが残りっぱなしになりリーク。テスターの malloc 失敗テストも落ちる |

## 完全トレース

**ファイル `"a\nbb\nccc\n"`（9バイト）を `BUFFER_SIZE=4` で読む。** `?` は未使用バイト、`·` は消費済み（`off` より前）。

### 1回目の呼び出し

| 処理 | `data`（cap の枠ごと） | `off` | `len` | `cap` |
| --- | --- | --- | --- | --- |
| 開始 | `NULL` | 0 | 0 | 0 |
| `fill_save`: `nl_pos(s,0)` → `-1`（空なので） | | | | |
| `buf = malloc(4)` | | | | |
| `read` → `"a\nbb"` (n=4)、`start = 0` | | | | |
| `append`: `off == 0` なので `compact` はスキップ | | | | |
| `grow(4)`: cap 0 → `BUFFER_SIZE+1 = 5`、**malloc①** | `? ? ? ? ?` | 0 | 0 | 5 |
| 4バイトコピー | `a \n b b ?` | 0 | 4 | 5 |
| `nl_pos(s, 0)` → `1` ✅ **read をやめる** | | | | |
| `str_line`: `pos=1` → `len=2`、**malloc②** で `"a\n"` | | | | |
| `consume(2)`: **`off` を進めるだけ（コピーなし）** ⭐ | `· · b b ?` | **2** | **2** | 5 |
| **戻り値 `"a\n"`** | | | | |

### 2回目 — ここで `compact` が働く

| 処理 | `data` | `off` | `len` | `cap` |
| --- | --- | --- | --- | --- |
| `nl_pos(s,0)` → `data[2],data[3]` = `"bb"` に `\n` 無し → `-1` | `· · b b ?` | 2 | 2 | 5 |
| `read` → `"\nccc"` (n=4)、`start = 2` | | | | |
| `append`: **`off != 0` なので `compact`** → 先頭へ寄せる | `b b b b ?` | **0** | 2 | 5 |
| `grow(2+4=6)`: 6 > 5 → cap **5→10**、**malloc③** | `b b ? ? ? ? ? ? ? ?` | 0 | 2 | 10 |
| 4バイト追記 | `b b \n c c c ? ? ? ?` | 0 | 6 | 10 |
| `nl_pos(s, **2**)` → `2` ✅（**新しい範囲だけ探した**） | | | | |
| `str_line`: `pos=2` → `len=3`、**malloc④** で `"bb\n"` | | | | |
| `consume(3)` | `· · · c c c ? ? ? ?` | **3** | **3** | 10 |
| **戻り値 `"bb\n"`** | | | | |

### 3回目 — `cap` の使い回しが効く

| 処理 | `data` | `off` | `len` | `cap` |
| --- | --- | --- | --- | --- |
| `nl_pos(s,0)` → `"ccc"` に `\n` 無し | `· · · c c c ? ? ? ?` | 3 | 3 | 10 |
| `read` → `"\n"` (n=1)、`start = 3` | | | | |
| `append`: `off != 0` → `compact` | `c c c c c c ? ? ? ?` | **0** | 3 | 10 |
| `grow(3+1=4)`: **4 ≤ 10 なので malloc しない** ⭐ | | | | |
| 1バイト追記 | `c c c \n c c ? ? ? ?` | 0 | 4 | 10 |
| `nl_pos(s, 3)` → `3` ✅ | | | | |
| `str_line`: `len=4`、**malloc⑤** で `"ccc\n"` | | | | |
| `consume(4)`: `len` が 0 になったので **`off` もリセット** | | **0** | **0** | 10 |
| **戻り値 `"ccc\n"`** | | | | |

### 4回目 — 終了

| 処理 | `data` | `off` | `len` | `cap` |
| --- | --- | --- | --- | --- |
| `nl_pos(s,0)` → `len=0` なのでループが回らず `-1` | | 0 | 0 | 10 |
| `read` → **`0`（EOF）** | | | | |
| `append(s, buf, 0)`: `compact` も `grow` も実質何もしない | | 0 | 0 | 10 |
| `nl_pos(s,0)` → `-1`、`while (n > 0)` が偽 → ループ脱出 | | | | |
| `s.len == 0` → `reset_save`、**free** | `NULL` | 0 | 0 | 0 |
| **戻り値 `NULL`** | | | | |

**確認ポイント**

- `grow` による `malloc` は①③の**2回だけ**（読み込み用 `buf` は毎回確保・解放、返す行は②④⑤）
- 3回目は容量が足りていたので `malloc` ゼロ。これが `cap` を分けて持っている理由
- `consume` は一度もメモリをコピーしていない。コピーが起きるのは `compact` が呼ばれたときだけで、**`read` 1回につき高々1度**
- `nl_pos` の `from` が 0 → 2 → 3 と進み、同じバイトを2度走査していない
- `NULL` を返す直前に必ず `reset_save` が走っている

> **`BUFFER_SIZE` が大きいとどうなるか**: 1回目の `read` でファイル全体が載るため、2回目以降は `nl_pos` の早期 return で終わり、`read` も `compact` も呼ばれません。`consume` が `off` を進めるだけなので、行数がいくら多くてもコピーは発生しません。前詰め方式ではここが `O(行数 × 残りバイト数)` になっていました。

## 理解度チェック（コードを見ずに答える）

<details>
<summary>1. <code>data</code> を <code>\0</code> 終端しないのはなぜ？ 終端したら何が変わる？</summary>

長さを毎回数え直す必要が出る（連結のたびに `O(N)` の走査）。また、`\0` を含むデータで行の切れ目を見失う。`len` を持てば終端記号は不要。ただし返す行は `\0` 終端が必須（呼び出し側が文字列として扱うため）。
</details>

<details>
<summary>2. <code>cap</code> を持たず <code>len</code> だけにしたら、何が壊れる？</summary>

正しさは壊れないが、追記のたびに `malloc` + 全コピーが必要になり `O(N²/BUFFER_SIZE)` に悪化する。実測で `BUFFER_SIZE=10` のとき malloc が 16回 → 2006回。
</details>

<details>
<summary>3. <code>fill_save</code> の冒頭で <code>\n</code> を確認しているのは最適化？ それとも正しさの問題？</summary>

**正しさの問題**。無いと、持ち越しだけで返せる行でも `read` を呼びに行き、パイプや端末では次のデータが来るまでブロックする。通常ファイルでは EOF が即返るので表に出ないが、標準入力から対話的に読むと1行ごとに固まる。
</details>

<details>
<summary>4. <code>consume</code> が「残りを先頭へ詰める」のではなく「<code>off</code> を進める」だけなのはなぜ？</summary>

前詰めだと1行返すたびに残り全部をコピーするため、`BUFFER_SIZE` が大きくてバッファにファイル全体が載っていると `O(行数 × 残りバイト数)` になる。実測で 20万行を `BUFFER_SIZE=10000000` で読むと 234 秒以上（`off` 方式は 0.19 秒）。`off` を進めるだけなら O(1)。
</details>

<details>
<summary>4b. <code>off</code> を進めるだけだと前方の領域が無駄になる。いつ回収する？</summary>

`append` の冒頭で `off != 0` のときだけ `compact()` が有効データを先頭へ寄せる。呼ばれるのは `read` 1回につき高々1度で、寄せる量もそのときの持ち越し分だけなので、全体では入力サイズに比例するコストに収まる。加えて `consume` は `len` が 0 になった時点で `off` を 0 に戻すので、行がぴったり消費されるケースでは `compact` すら不要。
</details>

<details>
<summary>5. <code>grow</code> の <code>if (cap == 0) cap = BUFFER_SIZE + 1;</code> を消すと？</summary>

**無限ループ**。`cap` が 0 のまま `cap *= 2` を回しても 0 のままで、`while (cap < need)` を抜けられない。
</details>

<details>
<summary>6. <code>str_line</code> の <code>*len = pos + 1</code> の <code>+1</code> を消すと？</summary>

区切り文字が持ち越しに残り続け、以降ずっと空文字列を返す無限ループになる。この `+1` が「返す行に `\n` を含める」という subject の指定そのもの。
</details>

<details>
<summary>6b. <code>nl_pos</code> と <code>str_line</code> の添字が <code>s->off + i</code> なのに、<code>nl_pos</code> の戻り値には <code>off</code> が入っていないのはなぜ？</summary>

戻り値も `*len` も `start` も、すべて**有効データの先頭から数えた相対位置**で統一しているから。絶対位置を返すと、`append` の中で `compact` が走って `off` が変わった瞬間に値が無効になる。相対位置なら `compact` の前後で意味が変わらない。
</details>

<details>
<summary>7. <code>static</code> を外すとどうなる？ なぜ？</summary>

未初期化のスタック領域をバッファのポインタとして扱い、`free` した瞬間にクラッシュする（実測で SIGBUS）。`static` はゼロ初期化が保証されるが、自動変数は保証されない。そもそも呼び出しをまたいで持ち越せないので機能しない。
</details>

<details>
<summary>8. <code>malloc</code> が失敗したとき、持ち越しバッファはどうなる？</summary>

`grow` は失敗時に `s` を一切変更しないので、古いバッファは無傷のまま残る。それを `get_next_line` が `reset_save` で解放してから `NULL` を返す。「`NULL` を返す経路はすべて `reset_save` を通る」が全体の不変条件。
</details>

<details>
<summary>9. <code>read</code> が <code>BUFFER_SIZE</code> より少ないバイト数を返すのはどんなとき？ コードのどこで対応している？</summary>

パイプ・ソケット・端末では日常的に起きる（ファイルでも EOF 直前）。`fill_save` が戻り値 `n` をそのまま `append` に渡し、`while (n > 0)` で読み足りなければ再度 `read` するので対応済み。`n` を `BUFFER_SIZE` と決め打ちすると壊れる。
</details>

<details>
<summary>10. <code>nl_pos</code> に <code>from</code> 引数があるのはなぜ？ 常に 0 でも動く？</summary>

動くが、追記のたびに先頭から走査し直すので長い行で `O(N²)` になる。`fill_save` が追記前の `s->len` を `start` として渡すことで、新しく読んだ範囲だけを見る。
</details>
